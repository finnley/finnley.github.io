## 什么是服务注册与发现

简单来说，当服务A需要依赖服务B时，我们就需要告诉服务A，哪里可以调用到服务B，这就是服务注册发现要解决的问题。

假如一个产品已经在线上运行，有一天运营想搞一场促销活动，那么我们相对应的【用户服务】可能就要新开启三个微服务实例来支撑这场促销活动。而与此同时，作为苦逼程序员的你就只有手动去 API Gateway 中添加新增的这三个微服务实例的IP与Port，一个真正在线的微服务系统可能有成百上千微服务，难道也要一个一个去手动添加吗？有没有让系统自动去实现这些操作的方法呢？答案当然是有的。

当我们新添加一个微服务实例的时候，微服务就会将自己的IP与Port发送到注册中心，在注册中心里面记录起来。当 API Gateway 需要访问某些微服务的时候，就会去注册中心取到相应的 ip 与 port。从而实现自动化操作。


## 基于配置文件的微服务弊端

常见的微服务可以通过配置文件很好的运作。

比如有个用户服务，它分为两层，上层 user-web 服务使用 Golang 开发，对外提供 HTTP 接口，底层 user-svc 使用 Python 开发，提供gRPC接口供 user-web 服务调用。当user-web服务调用user-svc服务时，需要知道被调方（user-svc）的IP与Port信息，否则就无法访问。

![alt text](/images/service-discovery/10.png)

被调方服务（user-svc）的配置信息以类似下面格式保存在调用方（user-web）的配置文件中：
```yaml
# 微服务名称
name: 'user-web'
port: 8021

# 上游被调用服务方
user_srv:
  host: '127.0.0.1'
  port: 50051
  name: 'user-srv'

...
```

这样user-web服务就可以通过本地配置文件中记录user-svc服务的信息来读取IP和Port，但如果底层被调用的服务越来越多，比如还有goods-svc商品服务、orders-svc订单服务、库存服务inventory-svc库存服务等，这些服务之间还会互相调用。

![alt text](/images/service-discovery/20.png)

实际中服务之间的调用非常复杂，通过配置文件读取的方式就需要保存很多对应的信息，就会越来越吃力，也就是每个服务都要保存并维护大量的配置信息。此时一旦出现了需求变动，比如： 

1. 新加一个服务，这个服务供其他很多服务调用；
2. 并发过高需添加机器。此场景简单的优化方式是另开机器或实例，这就需要知道新加的机器或新开实例的IP和Port，很多调用服务方就需要为新加配置重新部署，重新部署就可能出现错误，即改了一个服务需要其他服务重新部署）。

![alt text](/images/service-discovery/30.png)

面对上面场景，配置文件读取的方式就显得捉襟见肘，有新服务上线就得安排人员值守防止出现错误，服务之间也产生了强耦合。

## 注册中心

### 原理

针对基于配置文件的微服务弊端，可以通过`注册中心`来解决。

比如有个 user-svc，order-svc，这些底层上面还有对应的 user-web、order-web，这四层是互相独立的，它们对应4个不同的微服务。

1. 每个服务上线之前，或新加机或新开实例之前，先将自己的信息（IP和Port）上报到注册中心。
2. 访问其他服务时，比如user-web访问user-svc服务，user-web服务只需要到注册中心去拉取user-svc的信息（IP和Port），然后再通过拉取到的被调方IP和Port去连接被调方服务即可，其他服务也是同样的先到注册中心拉取，拉取之后就可以去连接访问其他服务了。

我们将信息的上报叫服务注册，信息的拉取叫服务发现。

### 实现

注册中心的实现可以考虑使用Redis，因为Redis可以实现注册和拉取的功能，但Redis并不能实现`健康检查`这个很重要的功能，所以实际场景中并不会使用Redis。

**健康检查**

比如服务将信息注册到注册中心，注册中心就有义务定时检查服务是否连通，这就是`健康检查`。

注册中心除了提供服务注册与发现、健康检查功能外，如果有同一批服务，注册中心还提供了识别并对这一批服务进行管理的功能，甚至还提供分布式的注册中心服务。

注册中心在稳定性、数据的一致性、分布式方面的要求都很重要。
